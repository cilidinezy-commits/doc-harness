# 底层分析：session 切换失败的证据与核心需求（Phase 5 调研笔记）

> 状态：调研笔记，非结论。目标是先把失败模式与需求看透，再谈设计。

## 失败模式（来自真实项目证据）

- **F1 入口文件分裂 / 过时**：一个大型下游项目 的 `AGENTS.md` 曾是 `CLAUDE.md` 旧快照 → 新 agent 按 AGENTS.md 进入拿到过时状态；某些 harness（DeepSeek Harness v0.1）会**同时读两份且不去重**，造成重复注入 + 计费翻倍。教训：入口必须单一权威，或"薄指针"。
- **F2 "当前状态"被历史淹没**：两个下游项目 头部堆满"(历史 phase)"、"(历史 One-line status)"，新 agent 找不到"现在"。
- **F3 手写的 compact 防御是"全量倾倒"而非"最小接手入口"**：一个下游项目 `context-archive-*-compact-defense.md` 是详尽 dump，靠 agent 自己在里面找"下一步"，缺一个"接手从这里开始"的最小块。
- **F4 "写下来"会被机制破坏且无人发现**：一个下游项目 记录过 CURRENT_STATUS 中文乱码（PowerShell 默认 GBK vs UTF-8），状态文档被写坏。→ 写文档要有编码/校验兜底。
- **F5 "更新状态"靠自觉、无守卫**：邮件轮询证据——轮询脚本只检测未读并唤醒；"处理后更新 CURRENT_STATUS"写在一个处理提示词里，靠 agent 自觉，无确定性校验。
- **F6 "新指令即丢线程"**：一个大型下游项目 的 `§0 全局棋盘` 治的是"新指令一来就丢当前线程"，说明断裂不止发生在跨 session，也发生在**指令切换**。

## 核心发现：一个大型下游项目 手工验证了正确的形态

它的"接手入口"天然分两层：

- **稳定层**：11 条"跨 session 必带的底层逻辑清单"，每条指向落档处，很少变（分层锚 / 哲学 / 设计思路 / 工作原则 / 铁律）。
- **当前层**：一个极小的"接手从这里开始"块——**在办（79号）＋先读（81→79→PHILOSOPHY §0/§16）＋今天的关键判断 / 归根 / 优先级变化**。

这正好对上用户的两条顶层判断：项目是"有结构的面"（在办是工作单元编号，非线性步骤）；真正要跨 session 的是"底层逻辑 / 哲学 / 原则"。

## 由此反推的核心需求（假设，待验证）

- **R1 入口唯一**：CLAUDE.md 唯一权威；AGENTS.md 只能是薄指针（或 doc-harness 明确哪份权威）。
- **R2 状态分层**：稳定层（底层逻辑/原则/锚，很少变）与当前层（在办/先读/关键判断，每 session 刷新）分离，且都与历史分离。
- **R3 当前层极小**：一屏内读完；只含"在办＋下一步＋先读哪几份＋关键判断"。
- **R4 可验证**：新鲜度、编码、是否真的更新过，都要有确定性守卫（红/提醒），不靠 agent 自觉。
- **R5 不干预工作方式**：以上都是"记录什么、放哪、怎么校验"，不是"agent 该怎么想/怎么做"。
